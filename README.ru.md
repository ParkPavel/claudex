# Клаудекс

**Один рабочий каталог. Общий контракт. Claude Code и Codex работают против одних и тех же улик.**

Клаудекс — небольшой локальный харнесс для разработки с участием моделей. Он держит
поддерживаемые инструкции в одном репозитории, выдаёт каждой задаче явную роль и снимок
исходников и отделяет заявление модели о готовности от проверенной приёмки. Профиль Obsidian
использует нативный Obsidian CLI для живых улик.

[English documentation](README.md) · [Архитектура](docs/explanation/architecture.md) ·
[Безопасность](SECURITY.md) · [Реестр улик](https://github.com/ParkPavel/claudex/blob/main/docs/research/evidence-register.md)

## Раскладка рабочего каталога

```text
your-desktop/                       # Локальный рабочий каталог; не публикуется
├── claudex/                        # Этот публичный репозиторий: политика и инструменты
├── your-project/                   # Отдельный Git-репозиторий
├── .local/claudex/                 # Локальная конфигурация, задачи, улики, резервные копии
├── .tmp/                           # Расходное; срок хранения выбираете вы
├── .claudex.json                   # Маленький указатель на локальное состояние
├── AGENTS.md                       # Сгенерированная точка входа Codex и общая
├── CLAUDE.md                       # Сгенерированная точка входа Claude
├── .codex/                         # Маленькие сгенерированные нативные описания ролей
├── .claude/                        # Маленькие сгенерированные описания ролей и навыков
└── .agents/                        # Маленькие сгенерированные точки входа навыков
```

Публикуется только `claudex/`. Хранилища, личные заметки, снимки экрана, переписка, учётные
данные и произвольные пользовательские папки остаются снаружи. Сгенерированные файлы ссылаются
на поддерживаемый контракт и навыки; `sync` сверяет их хеши перед обновлением.

## Начало работы

Нужны Node.js 22+, Git и авторизованные установки Claude Code и Codex. Профилю Obsidian
дополнительно нужны настольный CLI и выделенное тестовое хранилище. Windows и Linux покрыты
конфигурацией CI; результаты на живом хосте записываются отдельно.

```sh
git clone https://github.com/ParkPavel/claudex.git
cd claudex && npm ci
node bin/claudex.mjs setup --workspace ..
node bin/claudex.mjs doctor --workspace ..
```

`setup` открывает окно и спрашивает то, что установка не может решить за вас: каким проектом
она управляет, насколько много ей позволено без спроса и какая модель отвечает за какую роль.
Прежде чем что-то создать, окно перечисляет, что именно появится рядом с вашим проектом.
В скрипте те же решения принимает `init` флагами, без единого приглашения.

Управляемый проект должен уже быть Git-репозиторием рядом с `claudex`. Для Obsidian выберите
профиль `obsidian` и следуйте [руководству по Obsidian](docs/how-to/obsidian.md). Авторизация
остаётся в клиентах провайдеров; Клаудекс не копирует учётные данные к себе. Полный разбор —
[установка и настройка под себя](docs/how-to/setup.md).

### Из архива выпуска

Распакуйте `claudex-<version>.zip` рядом с Git-репозиторием, которым нужно управлять. В
Windows дважды нажмите `setup.cmd`; в Linux или macOS запустите `./setup.sh`. Лаунчер откроет
то же окно установки и возьмёт родительскую папку архива как рабочий каталог. Если нужен
другой рабочий каталог, передайте его путь первым аргументом.

Архив самодостаточен: runtime-зависимостей npm у Клаудекса нет, поэтому установка — это
распаковка и запуск лаунчера. Файл `.sha256` рядом с архивом идентифицирует полученные байты.
Мейнтейнер собирает и проверяет оба файла командой `npm run release:archive`.

## Настройка под свой стек

| Решение | Умолчание | Чем менять |
|---|---|---|
| Что писателю позволено без спроса | `approval` — одно записанное разрешение на задачу | `settings --access full\|scoped\|approval` |
| Какая модель отвечает за роль | Общая таблица ролей | `settings --assign architect=codex/gpt-5.6-terra@max` |
| Какие файлы принадлежат задаче | Объявляются задачей и заняты, пока она идёт | `worktree TASK --paths docs,src/lib` |

Чтение и ревью не ограничиваются никогда: режимы доступа различаются тем, что можно изменить,
а не тем, на что можно смотреть. Роль, которая пишет, нельзя назначить read-only провайдеру, и
отказ происходит там, где делается выбор, а не когда задача уже запущена.

## Ограниченная задача

Скопируйте [пример пакета](examples/map-task.json) в локальное хранилище и задайте цель, пути
и критерии. Из корня рабочего каталога:

```sh
node claudex/bin/claudex.mjs run .local/map-task.json --wait
node claudex/bin/claudex.mjs status
node claudex/bin/claudex.mjs cancel JOB_ID
```

Без `--wait` отправка возвращается сразу, а фоновый координатор выполняет ровно эту задачу.
Смотреть по идентификатору. `COMPLETED` означает, что провайдер вернул корректный результат;
`proposedAcceptance` — оценка самой модели. Приёмка задачи остаётся `UNKNOWN`, пока вне этой
оценки не записаны независимо разобранные улики.

Пишущей задаче нужны отдельный worktree и — в режиме по умолчанию — разрешение:

```sh
node claudex/bin/claudex.mjs worktree implement-one-change --base HEAD --paths src/lib
node claudex/bin/claudex.mjs approve implement-one-change --reason "План и его границы просмотрены"
```

Полученный путь укажите в пакете роли `implementer`. Управляемый работник Claude пользуется
ограниченными файловыми инструментами и не получает свободной оболочки. Проверки проекта
запускает координатор командой `check-project`. Закончив, снимайте чекаут через харнесс:
`worktree --retire` отцепляет общие ссылки на зависимости до того, как git удалит каталог.
Остальное — в [справочнике команд](docs/reference/commands.md).

## Что реализовано

| Возможность | Граница |
|---|---|
| Общие роли и пять сфокусированных навыков | Одно поддерживаемое тело, сгенерированные нативные точки входа |
| Структурированные задачи и общий предел параллельности | Управляемые задачи Клаудекса; сторонние сессии CLI вне планировщика |
| Закреплённые улики исходников и конфигурации | Полный Git HEAD плюс хеши отслеживаемого и значимого неотслеживаемого содержимого |
| Ревьюеры только для чтения | Read-only песочница Codex; ограниченные файловые инструменты Claude; повышения прав нет |
| Сбор улик Obsidian | Явная идентичность хранилища, локальные артефакты, шлюз изменений тестового хранилища |
| Ограждения публикации | Проверки секретов в индексе и истории, защищённые ссылки, fast-forward и запрет удаления |
| Видимость восстановления | Точные идентификаторы задач, дедлайны готовности, отмена и диагностика сирот |
| Окно установки | Проект, режим доступа, провайдеры и модели по ролям — до того, как что-то записано |
| Режимы доступа | `full`, `scoped`, `approval`; одноразовые разрешения тратит тот работник, который их использует |
| Заявки на области | Пишущие задачи объявляют и занимают свои файлы; перекрытие требует записанной причины |
| Видимость и снятие worktree | Незакоммиченное, незавершённые слияния и общие установки видны, ссылки отцепляются до удаления |
| Записанная передача провайдера | Кончившиеся токены становятся передачей с долгом перепроверки, а не тихой подменой |
| Журнал пушей | Каждый пуш через ограждение оставляет строку, написанную границей, а не автором |

Клаудекс 0.1.0 — первый инженерный выпуск. Он не заявляет превосходства в бенчмарках,
безупречного обнаружения секретов, автоматического восстановления осиротевших процессов или
самостоятельной продуктовой приёмки. Читайте [модель угроз](SECURITY.md) и
[границы проверки](https://github.com/ParkPavel/claudex/blob/main/docs/research/validation.md).
